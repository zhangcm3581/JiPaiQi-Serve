# 每租户保留5个历史版本与查询优化

## 保留范围

每租户保留最近5个已关闭版本，当前进行中的版本另算。按实际版本记录数量而非版本号差值处理，管理员跳号不影响保留数量。旧版本的rounds、hands、starts及requests确认缓存一起删除；客户端登记、last_bound和租户当前版本不删除、不回退。

首次启动新版服务时，先创建索引、记录当日汇总，再清理既有历史。此后在结束事务内淘汰第6个旧版本；不在收牌过程中批量清理。失败会回滚轮次推进及关联删除。历史API访问已删除版本返回404，页面说明仅保留5个版本。

保留窗口内原请求仍返回原ack；窗口外原轮次请求返回ROUND_CLOSED，客户端按既有恢复流程处理。去重缓存不再永久保留，客户端必须继续使用唯一请求/事件ID，不能把旧请求改标新版本。当前版本检查阻止原旧轮次重试串入新局。

## 查询优化

- starts_round：租户＋版本＋客户端＋事件，实时状态用覆盖索引，并合并原先重复的参与事件查询。
- requests_round：租户＋确认消息中的round_version表达式索引，清理按版本查找，不新增原表字段，兼容旧表结构。
- rounds_retention：按租户快速取得第6个已关闭版本。
- rounds_history、rounds_history_tenant：全局及租户历史排序。
- rounds_expiry：只索引未关闭版本的截止时间，超时扫描避开历史。
- rounds_ready：首次迁移按日期读取完成统计。

首页今日完成数和平均计算耗时改为当日聚合计数，不包含牌面，避免删除历史后统计减少；新日期完成计算时淘汰旧日期聚合。首次迁移在删历史前回填，重复启动不会重复计数。

## 验证结果

99项Python测试、10项管理后台JS测试全部通过。覆盖保留5局、当前局不丢失、租户隔离、跳号、旧请求、重新加入、今日统计、旧库迁移、失败回滚、超时与停用；20局真实WebSocket连续测试确认140份上报及结果正确，最后仅保留16—20版，当前21版不受影响。Python有2条依赖弃用警告，无失败。

隔离合成数据：单租户10000个旧版本、70000份历史手牌，当前状态读取各测50次：

| 状态 | 平均 | P95 |
| --- | --- | --- |
| 旧代码与旧索引 | 57.163ms | 58.045ms |
| 仅补参与事件索引，未删历史 | 0.335ms | 0.390ms |
| 完整新版，保留5局 | 0.357ms | 0.434ms |

清理后rounds共6行（5历史＋1当前），hands/starts/requests各35行。今日完成计数仍为10000。该测量仅为本机SQLite当前状态查询，不是公网或客户端显示耗时；证明索引消除了此查询随历史增长扫描的问题，不代表所有服务器请求提速同样倍数。

原始结果见verification/history-retention-20260912/。复测：先通过git show 00d134f:app/domain.py导出旧版到临时文件，再运行scripts/verification/history_benchmark.py --baseline-domain 临时文件 --output 结果.json。脚本只创建自动清理的临时数据库。

## 部署

仅更新服务端，客户端0.4.22不需更新。由操作者执行：

```sh
cd /opt/jpq
sudo bash scripts/update.sh
```

不要先手动git pull。脚本会备份数据库并重启；首次启动自动清理超出范围的历史，此后这些版本不能在后台展开。备份文件不受本保留策略影响。

删除行后SQLite文件未必立即变小，空闲页会复用。没有在实时业务中执行VACUUM，以免阻塞。此次未访问、清理或部署线上数据库。
